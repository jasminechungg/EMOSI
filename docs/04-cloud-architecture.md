# Cloud Architecture

## Cloud Architecture Overview

![AWS Cloud Architecture](../diagrams/system-architecture.PNG)

The EmoSI platform utilises a cloud-native architecture built on Amazon Web Services (AWS) to support real-time physiological data acquisition, processing, storage, machine learning inference, and dashboard visualisation.

The cloud infrastructure was designed to handle continuous physiological data streams generated by the EmotiBit wearable device while maintaining scalability, flexibility, and modularity. The architecture integrates multiple AWS services that work together to form an end-to-end emotion monitoring pipeline.

The cloud ecosystem consists of six primary layers:

1. Data Ingestion Layer
2. Stream Processing Layer
3. Storage Layer
4. Machine Learning Layer
5. Presentation Layer
6. Authentication Layer

These layers collectively enable physiological data collected from wearable sensors to be transformed into actionable emotion-related insights presented through an interactive dashboard.

## AWS Services Used

The following AWS services were utilised throughout the development and deployment of EmoSI.

| Service | Purpose |
|----------|----------|
| AWS IoT Core | Secure MQTT communication and device connectivity |
| Amazon Kinesis Data Streams | Real-time stream processing |
| AWS Lambda | Serverless data processing and orchestration |
| Amazon DynamoDB | Storage of physiological and prediction data |
| Amazon SageMaker | Machine learning model deployment and inference |
| Amazon S3 | Storage of datasets, model artifacts, and training resources |
| Amazon Cognito | User authentication and access management |
| boto3 | Dashboard communication with AWS services |

## Data Ingestion Layer

The Data Ingestion Layer is responsible for receiving physiological data transmitted by the EmotiBit wearable device.

### Components

- EmotiBit
- ESP32 Feather
- AWS IoT Core

The ESP32 microcontroller packages physiological sensor readings into MQTT messages and transmits them securely to AWS IoT Core using MQTT over TLS.

AWS IoT Core serves as the entry point into the cloud infrastructure by handling:

- Device authentication
- Secure communication
- MQTT topic management
- Message routing

This architecture enables reliable real-time transmission of physiological sensor data from wearable devices to cloud services.

## Stream Processing Layer

The Stream Processing Layer enables real-time processing of incoming physiological data.

### Components

- Amazon Kinesis Data Streams
- AWS Lambda

Incoming sensor data from AWS IoT Core is forwarded to Amazon Kinesis Data Streams.

Kinesis acts as a scalable streaming platform capable of buffering and distributing physiological data streams for downstream processing.

AWS Lambda functions are triggered by incoming records and perform:

- Data validation
- Data transformation
- Feature preparation
- Inference request generation
- Workflow orchestration

This serverless approach removes the need for dedicated processing servers while supporting near real-time processing.

## Storage Layer

The Storage Layer provides persistent storage for datasets, sensor readings, machine learning resources, and prediction results.

### Amazon DynamoDB

DynamoDB serves as the primary operational database.

Stored information includes:

- Physiological sensor readings
- Session records
- Emotion predictions
- User information
- Historical monitoring data

The database provides low-latency access for dashboard visualisation and machine learning workflows.

### Amazon S3

Amazon S3 serves as the central storage repository for machine learning resources.

Stored resources include:

- WESAD dataset files
- EmotiBit datasets
- Processed feature datasets
- Model artifacts
- XGBoost model files
- Label encoder files
- SageMaker deployment packages

S3 provides scalable and cost-effective storage for training and deployment resources.

## Machine Learning Layer

The Machine Learning Layer performs emotion recognition based on physiological sensor data.

### Components

- Amazon SageMaker
- XGBoost Emotion Model
- Training Datasets

The machine learning pipeline utilises a hybrid dataset approach combining:

- Publicly available WESAD data
- Manually labelled EmotiBit physiological data

Physiological signals undergo preprocessing and feature extraction before being used for model training.

The trained XGBoost model is deployed as a SageMaker Endpoint to support real-time inference.

The model currently supports recognition of:

- Happy
- Neutral
- Nervous
- Sad
- Angry

For each inference request, probability scores are generated for all emotion classes and the dominant emotion is selected based on the highest confidence value.

## Presentation Layer

The Presentation Layer provides user access to physiological data and emotion predictions.

### Components

- Streamlit Dashboard
- boto3 SDK

The Streamlit dashboard retrieves data directly from DynamoDB using boto3.

Dashboard capabilities include:

- Real-time physiological monitoring
- Emotion prediction display
- Dominant emotion visualisation
- Historical data review
- Session monitoring
- User management

The dashboard serves as the primary interface for reviewing physiological and emotion-related information.

## Authentication Layer

Amazon Cognito is used to manage authentication and access control.

Key responsibilities include:

- User registration
- User authentication
- Session management
- Access control
- Role-based permissions

The authentication layer ensures that only authorised users can access monitoring data and administrative functions.

## End-to-End Cloud Workflow

The complete cloud workflow follows the sequence below:

1. Physiological signals are collected by EmotiBit.

2. Sensor readings are transmitted through the ESP32 microcontroller.

3. Data is published to AWS IoT Core using MQTT.

4. AWS IoT Core forwards incoming records to Amazon Kinesis.

5. AWS Lambda processes incoming physiological data.

6. Relevant features are submitted to the SageMaker Endpoint.

7. Emotion predictions are generated by the deployed XGBoost model.

8. Sensor readings and prediction results are stored in DynamoDB.

9. The Streamlit dashboard retrieves records from DynamoDB using boto3.

10. Physiological data and emotion predictions are displayed to authorised users.
    
## Future Production Enhancements

The current implementation allows the Streamlit dashboard to communicate directly with DynamoDB through boto3. This approach was selected to simplify development and accelerate prototyping.

For larger-scale deployments, an additional API abstraction layer may be introduced:

Streamlit Dashboard → API Gateway → AWS Lambda → DynamoDB

Potential benefits include:

- Improved security
- Reduced direct database exposure
- Easier API versioning
- Better scalability
- Support for multiple client applications
- Improved maintainability

## Limitations and Considerations

Although the cloud architecture successfully supports real-time physiological monitoring and emotion inference, several considerations remain.

### Network Dependency

The platform requires stable internet connectivity for cloud communication and real-time monitoring.

### Service Costs

AWS service usage may incur operational costs depending on data volume, storage requirements, and inference frequency.

### Scalability Testing

Large-scale concurrent deployment scenarios were not extensively evaluated during this project.

### Model Dependency

Prediction quality remains dependent on the quality of physiological data and machine learning models.

### Future Optimisation Opportunities

Future work may include:

- API Gateway integration
- Event-driven microservices
- Automated model retraining pipelines
- Infrastructure-as-Code deployment
- Multi-user scalability enhancements
